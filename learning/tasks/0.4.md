## Зачем это в реальной жизни

В нормальной команде код не пишут, пока не договорились о контракте API. По такому контракту фронтенд и бэкенд работают параллельно, а QA заранее пишет проверки. Твой чертёж станет картой всего курса: эндпоинты из него ты будешь реализовывать модуль за модулем.

## Что сделать

Спроектируй API «Гильдии героев».

**Сущности:**

- **Герой** (`hero`): имя, класс (воин / маг / разбойник / целитель), уровень, опыт (XP), золото.
- **Квест** (`quest`): название, сложность (лёгкий / средний / смертельный), награда (золото и XP), статус.
- Герой может **взять** квест и **сдать** его, тогда он получает награду.
- **Таблица лидеров**: топ-10 героев по опыту.

1. В `learning/notes/0.4-guild-api.md` опиши **не меньше 10 эндпоинтов**. Для каждого укажи:
   - метод и путь;
   - что он делает (одна строка);
   - пример тела запроса (если оно есть) в JSON;
   - пример успешного ответа и его статус;
   - хотя бы один ошибочный статус и когда он возникает.
2. Обязательный минимум: полный CRUD героев (5 эндпоинтов), список квестов с фильтром по сложности, один квест по id, «взять квест», «сдать квест», таблица лидеров.
3. Продумай ошибки: героя не существует; данные кривые (уровень −5, пустое имя); квест уже взят другим героем.
4. Создай `backend/requests/guild.http` со всеми эндпоинтами из чертежа на адрес `http://localhost:3000`. Сейчас они ещё не работают, и это нормально: файл будет живым чек-листом курса. Используй переменную `@baseUrl`.

## Критерии приёмки

- [ ] Описано 10 и больше эндпоинтов, обязательный минимум закрыт.
- [ ] Имена единообразные: везде множественное число, один стиль регистра.
- [ ] Методы и статусы корректные: где-то будет `201`, где-то `204`, а ещё понадобятся `400`, `404` и `409`.
- [ ] Все примеры JSON валидные.
- [ ] `guild.http` содержит все эндпоинты и использует `@baseUrl`.
- [ ] Сценарий «новый герой → взял квест → сдал → попал в таблицу лидеров» проходится **только** твоими эндпоинтами.

## Как проверить самому

Пройди пальцем по сценарию из последнего критерия. На каждом шаге спрашивай себя: какой запрос я отправлю? Какой id я возьму из прошлого ответа? Что вернётся? Если на каком-то шаге id взять неоткуда, значит, в каком-то ответе его не хватает.

Пример переменной в `.http`:

```http
@baseUrl = http://localhost:3000

### Пример
GET {{baseUrl}}/health
```

## Автотесты

Автотеста нет: это чертёж. Наставник проверит его так же, как на ревью API-дизайна в команде.

## Подсказки

### Уровень 1 — намёк

Сначала выпиши все **существительные** (ресурсы), потом **глаголы** (действия). Большинство глаголов ложатся на `GET` / `POST` / `PATCH` / `DELETE`.

### Уровень 2 — направление

Действия вроде «взять квест» не похожи на CRUD. Обычно их выражают двумя способами: как **создание нового ресурса** (например, «назначение» героя на квест) или как изменение статуса существующего ресурса. Для конфликтов, когда квест уже взят, есть отдельный статус: `409 Conflict`.

### Уровень 3 — почти решение

Один из вариантов для «взять квест»: `POST /quests/:questId/assignments` с телом `{ "heroId": 7 }`, который возвращает `201` и созданное назначение. «Сдать квест» спроектируй сам в том же духе. Подумай, это создание чего-то или изменение статуса?

## ⭐ Звёздочка

Продумай для `GET /heroes` пагинацию и сортировку (какие query-параметры, какие значения по умолчанию) и **единый формат ошибки**, одинаковый для всех эндпоинтов.
